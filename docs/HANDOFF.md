# MT6250 模拟器接力文档（给下一个 AI / 开发者）

> 本文档写给**从零上下文接手**的 AI。读完本文 + `docs/mt6250-wiring.md` 即可继续开发。
> 所有结论都有实证（反编译/运行日志），标注「推测」的除外。

## 1. 项目是什么

MT6250（MTK 功能机 GSM/GPRS 基带 SoC，ARM7EJ-S ≈ ARMv5TE）的固件模拟器：

- **语言**：Zig 0.16（构建系统）+ Unicorn 2.1.4（CPU，源码 vendor 在 `vendor/unicorn/`，由 zig cc 直接编译，不用 cmake、不链系统库）+ SDL3（castholm/SDL 源码构建）
- **固件**：`res/AHONG50_...bin`（16MB NOR 整片 dump，已入库）
- **构建/运行**：`zig build run -- --lenient`（--lenient = 未映射读写自动映射 4KB 页放行）
- **测试**：`zig build test`
- **Windows 交叉编译**：`zig build -Dtarget=x86_64-gnu`（已验证）

### 1.1 构建环境注意（DSH 沙箱/只读 HOME 时必看）

这台机器的 `~/.cache/zig` 在沙箱里不可写，改 Zig 源码后重建会报
`sub-compilation of compiler_rt failed / ReadOnlyFileSystem`。解决办法是把全局缓存
指到工作区内（13 秒可重建完）：

```sh
ZIG_GLOBAL_CACHE_DIR=$PWD/.zig-cache/global zig build
```

**日志输出注意**：axe 日志写到 stderr，但**直接 `> file` 重定向会丢日志**
（Zig 0.16 的 `std.Io.File` 写入路径问题，只落盘最后一段）。要留存完整日志必须走管道：

```sh
./zig-out/bin/sf6250_zig_emu --lenient 2>&1 | tee run.txt
```

无 X11 环境（无头）时加 `SDL_VIDEODRIVER=dummy`，否则 SDL 建窗会 X 错误退出。

## 2. 启动链模型（四阶段，全部有实证）

```
1. BootROM   片上 mask ROM（无固件）→ 模拟器扮演它：
             拷 BL 全镜像到 SRAM 0x70008000、设 SP/CPSR、
             r4 = BootROM 上下文指针（关键！见 §4）
2. ExtBL     SRAM 0x70008000（镜像 0x800~0x2980）
3. BL2       XIP 0x10008060（镜像 ExtBL 区 0x8000~0xe2a0）← 已全程跑通
4. MAUI      入口 0x10020300（XIP；运行中还会把自身重定位到外部 RAM 0x84Exxxxx）← 已进入
```

阶段入口在镜像里是 Thumb 地址（0x10008061 / 0x10020301），但 **Unicorn 的 code hook
报的是取指地址（偶数）**，所以判阶段要用 0x10008060 / 0x10020300。

BL 最终会**跳转到 0x0** 调用 BootROM 安装在低 RAM 的函数——这是正常流程，
不是崩溃（模拟器的 `until=0` 哨兵曾因此误拦，已改为 0xFFFFFFF0）。

## 3. 已实现（machine.zig）

- **外设接线**（读回有意义值/写日志）：UART1/2/3（0xA006/7/0080000，16550）、
  CLK/PLL 0xA0050000、EMI 总线命令 0xA0180000、LCM 0xA0450000、ACFG 0xA0730000、
  **SF 串行 flash 控制器 0xA0140000**、**RTC 0xA0710000**（后两者见 §4.2）
- **BootROM 上下文合成**（`setupBootromContext`）：
  - ctx = 0x70041000（地址必须 > 0x70040000：BL 的 BSS 清理范围止于此）
  - ctx+0x000：TLV 记录（首记录 0x6b422101+4，终止符 0x6820d104）
  - ctx+0x208：**BRLYT 表副本**（镜像 0x200~0x408）——BL 校验 strcmp+槽位扫描
  - ctx+0x8A8：模式标志 bit1（填 0 走默认路径）
  - ctx+0x8DC：服务表指针 → 0x70042000
- **服务表** 0x70042000：+0x00/+0x08/+0x18/+0x34 四个函数指针（**必须带 Thumb 位！**）
  → 服务桩 0x70042100（movs r0,#0; bx lr，返回 0）
- **EMI 重映射**：0xA01800A0 首次写入触发——0x0 从只读 NOR 视图切 8MB 可写 RAM，
  并在 0x0 安装 BootROM RAM 函数（ARM: mov r0,#0; bx lr）——BL 会跳到 0x0 调用它
- **SRAM 2MB**（0x70000000）、**外部 RAM** 0x82000000+64MB、**flash XIP 窗口** 0x10000000
- **全镜像装载**：GFH 头链随载荷一起拷进 SRAM

### 4.2 本轮新接线的两个外设（卡点都在这里，已解决）

**0xA0140000 = SF（串行 flash）控制器**。BL2 的 flash 识别/FTL 初始化全程用它：

| 偏移 | 含义 |
|---|---|
| +0x00 | 控制/状态：bit2&bit3 同时置位 = 命令完成（固件轮询 bit1），bit0 = 忙 |
| +0x04 | 状态位（bit0 参与固件对 +0x00 bit4 的判定）|
| +0x10 | 写进数据窗口的**命令字节数** |
| +0x14 | 命令之后要**读回的响应字节数**（注意：不是命令！0x1000d8c2 存的是第 4 个参数）|
| +0x800 | 4 字节数据窗口：[0..len) = 命令/地址，[len..) = 响应 |

固件流程（XIP）：`0x1000a8b4 → 0x1000d968 → 0x1000d890`（低层，被拷到 SRAM
0x70004b80 执行，`0x1000a13c` 是 ARM veneer 跳 0x70004d31）。
命令字节序列实测：`AF`（读电子 ID）→ `9F`（JEDEC RDID，返回 `2c cb 18`，
命中固件自带支持表 XIP 0x1000ca2c 第一项 = 16MB NOR）→ 选中 Micron 参数集 →
`06/61/81/7A` 初始化 → 状态轮询 `05`（RDSR）/`70`（RFSR）。
**关键**：RDSR 必须回 `0x00`（WIP=0）、RFSR 回 `0x80`（P/E ready），
否则 XIP 0x1000a5da 的等待循环永不退出（实测 100M 条里刷了 55 万次 0x05/0x70）。
接上之后 SF 命令从 109 万条降到 **13 条**。

**0xA0710000 = RTC**（数据手册 RTC 章）。BL 0x70008f00 先读
RTC_POWERKEY1/2（+0x50/+0x54，正确值 0xA357/0x67D2）判断是否已解锁，
未解锁则写 RTC_OSC32CON（+0x4C）并**轮询读回比对**（写 0x1A57 → 0x2B68 → 0x040F，
每次超时 65536 次）。接线方式 = 寄存器文件（写入值原样读回），冷启动全 0，
所以固件走完整的「未解锁 → 初始化」路径，且读回立刻成功。

### 4.3 芯片识别（已解决）

MAUI 的芯片识别函数 XIP `0x10033338` 读 16 位的 `0xA0000000`（芯片 ID）与
`0xA0000008`（芯片版本），并用 `0x6218 + {0,1,0xb,0xe,0xf,0x42}` 组成的老 MTK
芯片 ID 表比对：

* **`0xA0000008` 必须等于 `0x625A`**（= "6250A" = MT6250A），否则一路 branch 到
  `0x1003346E` 比对失败 → 死循环刷 `"# HW=MT0000 , SW=MT625"`（实测 100M 条刷 24 次）
* `0xA0000004` 低字节 = 启动模式 / "Chip SW second version"：bit7=0 时 BL2 的
  `0x1000A15C` 返回 0（正常启动）；成功路径还会按 `"Chip SW second version: %02d"` 打印

接线：`chip_regs`（+0x00 = 0x6250 / +0x04 = 0 / +0x08 = 0x625A）。
**参考实现 run761 独立得到同一结论**（其 `[patch] 0xA0000008 pre-filled = 0x625A`）。

### 4.4 当前卡点：MAUI 的「RAM 补丁代码区」无人装载（0xF0700000+）

MAUI 的 XIP 代码里有一张**静态 ARM veneer 表**（`0x10078C00` 起，
`ldr pc,[pc,#-4]` + 目标地址），其中 `0x10078C78` 起的 **313 项指向
`0xF07270C1`~`0xF072C2CD`**（RAMF0 上部）。实测：

* `0x100283E0` 的分支条件是无条件的（`0x1008B620` 就是 `movs r0,#1; bx lr`），
  所以这次调用**按固件设计必然发生**
* **没有任何东西写过 0xF0700000~0xF0800000**：BL / BL2 镜像里连该地址范围的字面量
  都没有（扫描结果 0 处）；MAUI crt0 的段表（`0x100C385C`~`0x100C39C8`）目标只有
  0x70008000/0x7000A800/0xF03B72DC/0xF05E2D74/0x7EB000/0x7F1000；运行时写监视
  （`[RAMF0写]`）在该区间**零命中**
* 该区域内容全 0 → 取指拿到 Thumb `0x0000`（NOP），一路滑到映射顶端 `0xF0800000`
  后 `fetch unmapped` 停机（状态：`[RAMF0执行] ... [RAMF0滑行]`）

**已用 IDA + 全量扫描排除的可能来源**（2026-10-06，避免后人重复劳动）：

| 假设 | 验证方式 | 结论 |
|---|---|---|
| BL/BL2 用固定地址搬 | 扫 flash 0x800..0x2980 与 0x8000..0xe2a0 里的 0xf07xxxxx 字面量 | **0 处** |
| MAUI crt0 段表搬 | 段表 0x100C385C~0x100C39C8（IDA 反编译 0x100C347C/0x100C3570 的 ARM 装载器）目标只有 0x70008000/0x7000A89C/0x200/0xF03B72DC/0xF05E2D74/0x7EB000/0x7F1000 | 不含 0xF07xxxxx |
| 某条 GFH 记录搬 | 全镜像搜 32 位字面量 0xF0700000 / 0xF0727000 / 0xF0710000 / 0xF0720000 | 0xF0700000 只出现 1 次且在熵编码数据里；其余 0 处 |
| 是某个 flash 连续块的搬迁 | 全量指纹扫描（313 个 veneer 目标 × 全 flash 所有可能基址，Thumb 序言匹配） | 最高命中 43/313 = 噪声，**不是连续拷贝** |
| 有人运行时写 | RAMF0 写监视（0xF0700000~0xF0800000，前 16 次带 pc/lr） | **零命中** |
| 有代码读这张表（当数据用） | 搜 veneer 表地址 0x10078C00/0x10078C78 的引用 | **0 处**（表是逐项被 `bl` 的 trampoline，每项仅 1 个调用者） |
| 传输/DMA 引擎搬运 | 0xA0520000 寄存器写现场（IDA 反编译 0x1003267A~0x100326FA） | 全程只 7 次写（+0x10..+0x28），是配置而非描述符 |

⇒ 该区域（0xF07270C1~0xF072C2CD）**既不由镜像装载、也不由固件写入**；要么是
BootROM/硬件的职责，要么落在我还没建模的某条搬运路径上（下一步方向）。

**临时诊断开关 `--ramf0-lr`**：遇到 0xF0700000+ 取指时等价 `bx lr` 直接返回
（参考实现 run761 run539 也把这里当「RAM 区域被误执行」用 lr 返回）。
打开后 MAUI 立刻继续跑，并打印固件自己的断言/日志：

```
[1] Assert fail: Caller Address: 0x1002AE91 Line: 104 - UNKNOWN
    Product: 11B AHONG50_11B Version: D27D__11B.W11.32__V0010
    BuildTime: 2013/04/23 20:06
addr:0x1007BD14 ... Memory dump is disabled! ...
```

最终停在 **`0x1002E38A` 的 `b .`**：

```asm
1002E37E: ldr  r0, [pc,#0x14]
1002E380: ldr  r1, [pc,#0x14]
1002E382: strh r0, [r1,#8]
1002E384: movs r0, #1
1002E386: bl   0x10037A84        ; 开中断：[0xA0030000] |= 0x2200 | bit0
1002E38A: b    .                 ; 等定时器 IRQ 启动 OS 调度
```

**参考实现独立确认**这一点：「MAUI 初始化完成死循环 0x1002E38A（Thumb b .）。
硬件初始化完成，中断已使能 (0x10037A84)，进入主循环等定时器 IRQ 启动 OS 调度」。

⇒ **下一个卡点是中断/定时器**（见 §9），不是外设轮询，也不是「再接线就好」的类型。

### 4.5 中断体系（IDA 反编译已摸清，交接要点）

* 中断号寄存器 `0xA07601A0`（bit8=无中断/低 8 位=号）、确认 `0xA07601A8`
* ISR 分发器 `0x10021F50`（镜像内无调用者 → 由中断入口回调）→ LISR 表
  `0xF03D0310+12*irq`；注册函数 `0x10092A08(irq, handler, name)`
* 实测中断号：11=OSTD（OS timer）、12=FM、18=GPT
* 异常向量表在低 RAM 0x0（MAUI 镜像 0x10020300 拷过去），IRQ 槽 → `0x700096B0`，
  该处是 **ARM** 代码（MAUI crt0 从 flash 0x872548 拷 0x20A8 字节到 0x70008000）
* 模拟器已实现手工 IRQ 交付（`--tick=N` / `--tick-irq=`，默认关闭），
  坑：SPSR 必须在切模式**之后**写；交付前必须查 CPSR.I（否则中断风暴）
* **当前结论**：固件开了中断控制器，但 CPSR.I 全程为 1（100M 条采样无翻转），
  所以「启动 OS」的代码就是被 `--ramf0-lr` 旁路掉的 RAM 补丁调用 —— 两个未解问题
  （RAM 补丁区装载者 / OS 启动）是同一个问题

**方法论**（已验证有效，勿改）：遇到新卡点 → PC 轨迹定位循环 → capstone 反汇编目标
（注意 ARM/Thumb 模式，运行时内存可能 ≠ 静态镜像）→ 确认轮询的寄存器/缺失的数据 →
接线或合成数据 → 重跑。**先看直方图/访问计数，再动手**——本轮两个卡点都是靠
「谁在访问 + 访问了多少次」定位的。

## 7. 铁律（前一个 AI 用 761 轮补丁换来的教训 + 本轮验证）

1. **函数指针必须带 Thumb 位（bit0=1）**——否则 blx 切 ARM 模式执行 Thumb
   字节 → 条件跳过 → 滑进零区。已犯过两次（服务表、GFH 交接）
2. **hook 报的 pc 是取指地址（偶数）**——用镜像里的 Thumb 入口地址（奇数）
   做 `pc ==` 判断永远不成立（本轮 ★ 阶段日志就是这样漏报的）
3. **不跳过任何初始化**——跳过的会在十万里之外爆炸（前 AI 的 761 轮补丁地狱）
4. **stub 必须有名字和依据**——每个接线的外设/合成的数据都要能回答
   「为什么是这个值」（例：SF 的 JEDEC ID 取自固件自带支持表第一项，
   而不是随手编一个）
5. **运行时内存 ≠ 静态镜像**——0x70009900~0x70009b40、0x70004b80~0x70005xxx
   是运行时写入/拷贝的代码，静态反汇编不可信；断点时刻 dump 运行时内存再反汇编
6. **Zig 侧陷阱**：函数指针/内存写入的常量不要在多处硬编码；C 回调不能传播
   错误（用 catch）；`until=0` 哨兵会拦截合法跳转；**日志不能直接重定向到文件**

## 9.7 下一会话的第一个任务（2026-10-07 收尾）

`--tick=50000` 交付的中断 11（OSTD）会让 OSTD handler（LISR 11，
0x70009529，**运行时码**——静态镜像乱码）挂死：它轮询 OSTD 寄存器
（0xA01F0040 区，注册时写 halfword 0x1F）的某状态位，读 0 永不就绪。
挂死耗尽全部预算，后续流程（含关机自旋 0x1002e38a 断点，已重建于
diag.zig）无法到达。

**做法**：预算临时降到 10M → 停机 dump 已含 0x70009500 运行时码
（RUNTIMEMEM:70009500）→ capstone 离线解码 → 找到轮询的寄存器/位 →
periph.zig 接线 OSTD 状态位（tick 交付时置位）→ handler 返回 →
流程继续 → 关机断点（0x1002e38a）触发 → 回溯关机决策。

注意：`| head` 会 SIGPIPE 杀模拟器；axe 日志有缓冲，超时杀进程丢日志，
务必让进程干净退出（预算 ≤ 实际可跑量）。

## 9.8 关机问题的根因已定位（2026-10-07，实测闭环）

**结论：关机不是「main() 正常退出」，而是一个 assert 失败后的 fatal error 路径。**
真机不会走这条路——是我们的 `0xA0520000` 传输引擎没实现真实搬运，导致固件
的自校验失败。完整因果链（每一环都有实测证据）：

```
MAUI main() 0x10020484
  → 0x1002ae90（读 ALICE 结构 [r0+0x10]）
  → 0x1002E100(r0=0x108E65A8, r1=100)     ← 异常上报入口
  → 0x100324b8：校验 *(0x108E65A8) == "ALICE_1"   ✅ 通过
  → 配 DMA：+0x00=0x10947980(起始) +0x04=0x10F39680(结束)
            +0x08=0x10DA1A68 +0x0C=0x2000 +0x2C=0xFFF +0x32=0x1000
            +0x80=1 启动；轮询 +0x34 bit31 = 完成
  → 0x10032714: cmp *(0x10947980), "CAKE"  ❌ 失败（我们是 0x83276380）
  → 0x1007bd0e assert 失败 → 0x1008b7a8 打印
       "[1] Assert fail: Caller Address: 0x1002AE91 Line: 104"
  → 0x1003092e "Memory dump is disabled!" → "If you want to do memory dump…"
  → 0x100308cc: cmp *(0xF03CFE24), 0x26409001  ❌（magic 没写）
  → 0x1002e358 关机函数 → 写 0xA0030008=0x1971 → 0x10037A84(1) → 0x1002e38a `b .`
```

### 关键事实（都有实测/反编译依据）

| 地址 | 含义 |
|---|---|
| `0x1002E100` | 异常上报入口：`cmp r4,#0x64` → `bl 0x100324b8` |
| `0x100324b8` | ALICE_1 逐字节校验（'A''L''I''C''E''_''1'）→ 配 DMA → 结果校验 |
| `0x10032714` | `cmp *(0x10947980), 0x454B4143("CAKE")` —— **本次关机的直接失败点** |
| `0x1007bd0e` | assert 失败函数（校验失败都 `bl` 到这里） |
| `0x108E65A8` | ALICE_1 结构（全镜像**只有这一处** "ALICE_1"）；+0x0C=0x10DA1A68、+0x10=0x10DD1358、+0x14 起 = 4,6,8,9,b,c,d（DMA 配置值） |
| `0x10947980` | CAKE 目标；`0x100216e4` 有个函数硬编码返回它。静态 flash 是高熵数据（压缩/加扰），真机由传输引擎装载 |
| `0x100308cc` | 关机决策点：`*(0xF03CFE24) != 0x26409001` → `bne 0x1003092e` |
| `0x10021c74` | magic 0x26409001 的**唯一**写入点，前置条件 `sub_10092E04()==1`（读 `*(u16*)0xF03D004E`，该变量只被 crt0 清零、无人写）→ 所以 magic 永远是 0 |

### 已验证的绕过（诊断开关 `--cake-patch`）

DMA 启动（`0xA0520080` 写 1）时把起始地址处写成固件期望的 "CAKE"
（依据：固件自己在 `0x10032714` 比的期望值）。实测：

```
[cake-patch] DMA 启动 → 起始 0x10947980 写入 "CAKE"
[DMA校验] 实际=0x454b4143 期望=0x454b4143 → 通过      ← assert 不再触发
执行 3851865 条指令, 最终 pc=0x109479a2  cpsr mode=0x13 (SVC)
```
**MAUI 不再关机**，并且跳进 `0x10947980` 区域执行——证明那里是**解压后的代码区**（
`0x100216e4` 返回该地址、DMA 把它配成传输目标，两者互证）。

### 下一步（真正的修法，不是打补丁）

`0xA0520000` 传输引擎要**真的把压缩数据装载到 `0x10947980`**：

1. `0x10947980` 起必须是**可写**的（真机是 RAM，不是 NOR XIP）。
   诊断开关 `--flash-rw` 已能验证：即使可写，**没有任何固件代码写它** → 只能由
   DMA 硬件装载。
2. 需要还原装载/解压算法。已知：目标范围 `0x10947980~0x10F39680`（约 10.4MB），
   块参数 `+0x0C=0x2000`、`+0x2C=0xFFF`、`+0x32=0x1000`，源描述符表
   `0x10DA1A68`（每项 4 字节，形如 `0xA88E65CC`，高字节像标志、低 3 字节像
   `0x10`+偏移）。
3. 当前 `--cake-patch` 之后的新卡点：`UC_ERR_INSN_INVALID @0x109479a2`
   —— 只补了前 4 字节，后面仍是压缩数据。解压实现到位后这个 patch 应删除。

### 顺带修掉的一个模拟器 bug（与关机无关）

`irq_active` 原来只在「PC 回到中断点」时复位。Nucleus 会在中断里切任务，
根本不回到中断点 → `irq_active` 永久为 true → tick 只交付 **1 次**、且关机断点
（在 `else` 分支里）永不触发。已改为「离开 IRQ 模式（0x12）即复位」。
另外 tick 交付现在加了「不在 IRQ 模式」的条件，防嵌套风暴。

**对照实验（重要）**：`--tick=0` 与 `--tick=50000` 走**完全相同**的关机路径，
只是指令数不同（7.36M vs 3.86M），且 tick=0 时 CPSR 是正常的 SVC（0x13）。
⇒ 关机与中断/tick 无关，别再往那个方向查。
