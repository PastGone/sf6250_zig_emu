# MT6250 接线情报（自 run761 单文件蒸馏）

来源：`docs/mt6250-sim-run761/mt6250-sim/src/main.c`（另一条模拟器路线的
7583 行单文件，run307~run761 逐轮点补的产物）。**只取接线事实**——它的
做法（手动进 BL2 入口、伪造 tick、栈帧手术）我们不采用，理由见
`git log` 的路线讨论与下方「教训」节。本文每条标注用途与验证状态。

## 启动链（四阶段，已由我们独立验证）

1. BootROM（片上，无固件，我们模拟其行为：装载 BL 进 SRAM 并跳转）
2. **ExtBL**（SRAM 0x70008000，即镜像 BL 区 0x800..0x2980）——EMI 配置、
   安全校验、GFH 解析、加载重定位、内核数据结构初始化。
   ✅ 我们验证：`custom_emi_MT6250.c`/`bl_Secure_v5.c`/`SSS_secure_shared_v5.c`/
   `bl_Main.c`/`bl_FTL.c` 源文件名字符串嵌在 0x114e~0x1d62，就在这段里。
3. **BL2**（XIP，镜像 ExtBL 区 0x8000..0xe2a0，入口 0x10008061）
4. **MAUI**（入口 0x10020301）。⚠️ 修正旧认知：MAUI **不是 XIP**——
   被重定位到外部 RAM **0x84Exxxxx** 执行（run688 注释：32MB 不够用 64MB）。

## BL（SRAM 阶段）死循环点与状态位（第 2 步核心）

> 以下补充 2026-10-05 自然启动实测（我们现在已推进到 390 万条指令）：

- **PLL 锁定**：BL 0x7000868e 三指令轮询 `0xA0050318` **bit1**（写
  0xA0050300/0x308 配置后等锁定）——已接线：读回 bit1=1
- **时钟切换三步握手**（BL 0x70008aac~aba，r1+0x24 = `0xA0050090`）：
  写 `0x300F0000` → 等 bit7=1；写 `0x700F0000` → 等 bit7=0；字面量池
  还有 `0x100F0000`（第三段，推测同 1）。已接线：按命令应答状态位
- **EMI 校准例程**（BL 0x70008fa4~fee，有限迭代）：写命令 0x11 到
  0xA01800A0 → 等 bit0=0 → 读 0xA01800A8/B8 测量值 → 计算 → 写回结果。
  已接线 busy 位后整段自然跑完（迭代 r2→r6）
- **当前卡点**（第 2 阶段最后一公里，2026-10-05 深挖结论）：
  崩溃链 = 0x70009688 `blx [[0x7000a114]]` 跳 0。追因结论：
  * 回调表 0x7000a114 注册值 = [arg1 + 0x8DC]（0x70008324~2a），
    arg1 = **r10(sl) 平台寄存器 = 0** → 落到 flash 视图 0x8DC = EMI_INFO
    首参数字 0x38a11a43，被当「结构体指针」注册
  * sl 本该指向**运行时构建的镜像参数表**（RAM 里的 GFH/参数副本，
    指针已修正）；sl=0 说明第 2 阶段内一个更早的「拷贝镜像头/建表」
    步骤没有以正确地址运行，或其结果被踩
  * 已排除：r0=0x8d3b2a23 不是垃圾——是 0x700082ac XOR 校验函数对
    某镜像区算出的校验和，经 r9(fp) 跨 RAM 蹦床（0x700099c8 veneer，
    mov r7,lr 保存返回链，会清 r0-r3、r7）传递
  * 关键认知：SRAM 0x70009900~0x70009b40 区域的代码**运行时与静态
    不同/混合模式**（ARM 蹦床 + Thumb），静态反汇编不可信，必须 dump
    运行时内存再解（machine.zig 断点已内置导出）
  * 下一步：找「谁设置 sl(r10)」——Thumb 高寄存器 mov（0x46xx 系列）
    或 ARM 0xE1A0A00X；以及 0x70008220 `blx 0x700082ac` 的分发上游
  * 2026-10-05 续：init_dispatch 反编译确认（a1/a2 存全局 0x7000A0E0/E4、
    写 0xA0030008=0x1971 两次、条件写 0xA0010320=1、尾部
    sub_70008C10(0x70008000)）；全 BL 静态代码**零处**给 sl 赋值；运行时
    区域（0x700092xx+）把 sl 当边界用（cmp r5, sl），0x70009b72 /
    0x70009d0e 有 pop.w 从栈恢复——赋值源头在这些函数的上游，或在
    **BootROM→BL 的寄存器交接**（模拟器目前只设 PC/SP/CPSR，其余全 0）
  * 模拟器已补：外部 RAM 0x82000000+64MB RWX（MAUI 重定位目标）、apb 段
    收窄到 0x80000000+32MB（原 256MB 与外部 RAM 重叠导致 UC_ERR_MAP）
  * **2026-10-05 定性**：ARM 分发链（0x70008200~0x7000823c）完整拆出——
    一串 blx 固定地址的初始化步骤，`mov r0, sl` 把 sl 作为上下文指针
    一路传给各初始化函数，最后 init_dispatch(a2=sl) 用 [sl+0x8DC] 注册
    回调表。**全镜像无任何 sl 赋值 → sl 是 BootROM 交接的上下文指针**
    （对应镜像内 _MINI_EXT_SHR_DATA_ / BL_DA_SHARED_DATA_HEADER 结构，
    ≥0x8E0 字节）。模拟器 r10=0 启动 → 建表操作全写零页、读回垃圾
  * 收尾路径：从 0x70008266（第一个吃 sl 的函数）反编译确定 sl 结构
    布局，在模拟器里合成该结构并让 BootROM 交接时放入 r10
  * **Thumb 位教训**：所有函数指针必须 bit0=1。服务表第一版漏了 Thumb
    位，blx 切到 ARM 模式执行 Thumb 桩字节 → 条件跳过 → 顺序滑过四个
    服务桩 → 落入零区 NOP 滑行到 SRAM 边界。症状：四个服务「被调用」
    但轨迹线性无返回——看到服务地址连续排列就该想到模式问题
  * 新边界：四个服务返回 0 后，流程推进到 sub_70008C10(0x70008000)
    （记录定位 + 入口计算：TLV 查 type=2/type=0 记录、算 [r+0x1c] +
    [r+0x28] + 0x24 的组合指针），随后 pc=0——下一层待合成数据
  * **ctx+0x208 = BRLYT 表副本（已合成）**：sub_70008266 校验
    strcmp(ctx+0x208,"BRLYT") + 扫描 index==2 的槽位（= ExtBL！），
    找到后调 0x70008e78 装载器。副本来自镜像 0x200~0x408。
    **实测：0x7000825c 错误自旋通过**，BL 进入 ExtBL 装载阶段，
    新外设 0xA014xxxx（SF 控制器）/ 0xA071xxxx（RTC）出现
    ——**2026-10-06 已接线，见下方「BL2 阶段」一节**
  * BootROM 上下文布局总结：ctx+0x000 TLV 记录 / +0x208 BRLYT 副本 /
    +0x8A8 模式标志 / +0x8DC 服务表指针——即 BootROM 把固件头部区
    （file 0x0~0x900+）拷进了上下文
  * **2026-10-05 深夜定案（模拟器扮演 BootROM 已实现）**：
    - 入口指令流实测：mrs cpsr → orr #0xC0 关中断 → **mov r10, r4** →
      blx 初始化链。**BootROM 把共享数据指针放在 r4**，BL 拷进 r10
    - 模拟器合成：ctx=0x7000d000（TLV 首记录 0x6b422101+4、终止符
      0x6820d104、[+0x28]=TLV 大小、[+0x8A8]=0、[+0x8DC]=服务表
      0x7000e000）；服务表 +0x00/+0x08/+0x18/+0x34 → 服务桩
      0x7000e100~（movs r0,#0; bx lr，返回 0）
    - EMI 总线命令（0xA01800A0 首写）触发 0x0 重映射：NOR 视图 → 8MB RAM
      （BL 在 0x0~0x8E0 建共享数据，原 NOR 只读视图会吞掉写入）
    - SRAM 扩到 1MB（run761 地图；256KB 时 pc 冲出 0x70040000）
    - 实测：init_dispatch 注册表项 = 0x7000e000 ✓；四个 BootROM 服务全部
      被调用（r0=0x10）✓；BL 推进到 416 万条，进入「BSS 重清 +
      init_dispatch 重入」的阶段交接形态，当前停在 blx 0x70100000
      （恰好 SRAM 顶，跳转目标来源待查——疑似下一阶段重定位入口）
  * **2MB 实验**：停点随映射边界移动（0x70100000 → 0x70200000）——CPU 在
    清零区里滑行（Thumb 0x0000 = NOP）。BSS 清理函数被「逐字递进」调用
    （r0 每次 +4，区间 [0x70004a00, 0x70005970)，约 988 次）= 初始化在
    逐字建低 RAM 数据区。待查：后续清理阶段的范围（cap 32 已截断）、
    init_dispatch 重入语义、0x70200000 跳转的来源

- `0x70008AAC` 轮询 **0xA0050090** bit7（时钟/PLL）：写 0x300F0000 → 等
  bit7=1；写 0x700F0000 → 等 bit7=0
- `0x70008FA8` 轮询 **0xA01800A0** bit0（EMI/总线命令）：写 0x11 → 等 bit0=0
- 0xA0050090 bit0 = EMI busy（写命令后自清）
- 我们实测补充：BL 还在 `0x1ffffffe` 做半字读（RAM 容量探测，按位踩地址顶）
  ——EMI 重映射 0x0 区域为 RAM 后自然通过

## ## BL2 阶段（第 3 步，已全程跑通）——SF 串行 flash 控制器 + RTC

> 2026-10-06 实测补充。BL2 入口取指 0x10008060（镜像标 Thumb 入口 0x10008061），
> 在第 2,740,305 条指令进入；此后 BL2 完成 flash 识别、FTL 初始化，
> 打印 `~~~ Welcome to MTK Bootloader V005 (since 2005) ~~~`、
> `Bye bye bootloader, jump to=0x10020300`，随后进入 MAUI。

### 0xA0140000 = SF（串行 flash）控制器（**数据手册里没有，靠固件行为反推**）

固件调用链（全部 XIP，低层例程被拷到 SRAM 0x70004b80 起执行）：
`0x1000a8b4`（读 ID）→ `0x1000d968`（发 1 字节命令读 3 字节）→ `0x1000d890`
（低层：写数据窗口 / 置长度 / 启动 / 等完成 / 读回）；
`0x1000a13c` 是 ARM veneer（`ldr pc,[pc,#-4]`）→ SRAM `0x70004d31`。

| 偏移   | 读写 | 含义                                                                         |
| ------ | ---- | ---------------------------------------------------------------------------- |
| +0x00  | R/W  | 控制/状态。固件写 bit3 起命令、写 `bit2                                      | bit3` 启动；轮询 bit1=完成、bit0=空闲 |
| +0x04  | R/W  | 状态位；bit0 参与固件对 +0x00 bit4 的判定                                    |
| +0x10  | W    | 写进数据窗口的命令字节数（命令 + 地址）                                      |
| +0x14  | W    | 命令之后要**读回的响应字节数**（**不是命令**：0x1000d8c2 存的是第 4 个参数） |
| +0x800 | R/W  | 4 字节数据窗口：`[0..len)` = 命令/地址，`[len..)` = 响应                     |

固件实际发出的命令（实测，按序）：`AF`（读电子 ID，回 0 即视为不支持）→
`9F`（JEDEC RDID，必须命中固件自带支持表 XIP `0x1000ca2c`：第一项
`03 03 2c cb 18` = 16MB NOR）→ 选中该 ID 的参数集（Micron 风格）→
`06`(WREN)/`61`/`81`/`7A` 初始化 → 状态轮询 `05`(RDSR)/`70`(RFSR)。

**关键值**：`05` 必须回 `0x00`（WIP=0）、`70` 必须回 `0x80`（P/E ready）。
否则 XIP `0x1000a5da` 的状态等待循环永不退出——实测 100M 条里刷了
549,222 次 0x05 + 549,222 次 0x70；改对之后总共只有 **13 条** SF 命令。

### 0xA0710000 = RTC（数据手册 RTC 章有完整定义）

BL `0x70008f00`：
1. 轮询 `RTC_BBPU`(+0x00) bit6 直到 0（上限 65536 次）
2. 读 `RTC_POWERKEY1/2`(+0x50/+0x54)，等于 `0xA357`/`0x67D2` 就认为已解锁并直接返回
3. 否则写 `RTC_OSC32CON`(+0x4C)：`0x1A57` → 等读回相等 → `0x2B68` → 等读回相等 →
   `0x040F`（bit5=0 时；bit5=1 时 `0x042F`）→ 等读回相等（每步超时 65536 次）

接线方式 = **寄存器文件（写入值原样读回）**，冷启动全 0 → 固件走完整初始化路径，
且读回立刻成功（真机是写进 RTC 时钟域后同步回来，终点状态一致）。

### 0xA0000000 = 芯片标识/启动模式寄存器（16 位）

| 偏移  | 含义                                                                    | 值                             |
| ----- | ----------------------------------------------------------------------- | ------------------------------ |
| +0x00 | 芯片 ID                                                                 | 0x6250（MT6250）               |
| +0x04 | 启动模式 / "Chip SW second version"（低字节）                           | 0（bit7=0 → BL2 判定正常启动） |
| +0x08 | 芯片版本 —— MAUI 识别函数 XIP 0x10033338 **要求等于 0x625A**（"6250A"） | 0x625A                         |

依据：MAUI 0x10033338 的比对表（`0x6218 + {0,1,0xb,0xe,0xf,0x42}`）、
BL2 0x1000A15C 的启动模式判定、成功路径的 `"Chip SW second version: %02d"` 打印；
参考实现 run761 独立得出同一结论。

### 中断体系（IDA 反编译实证，2026-10-06）

| 地址                             | 作用                                                                       | 依据                                                           |
| -------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `0xA07601A0`                     | **当前中断号**：bit8=1 表示无中断，否则低 8 位是中断号                     | `sub_100230A0` 原文：`if (v & 0x100) return -1; else return v` |
| `0xA07601A8`                     | 写 = **确认**（ack）该中断                                                 | `sub_10021F50` 尾部 `[0xA07601A8] = irq`                       |
| `0xA0030000`                     | 全局中断控制（16 位）：`0x10037A84` 读改写 `                               | = 0x2201`（bit0=开）                                           | MAUI 收尾 `sub_1002E358` 调用 |
| `0xA0030008`                     | 16 位，MAUI 收尾写 `0x1971`                                                | 同上                                                           |
| `0xA0060040/44`                  | 中断**使能**置位（`1<<n` 掩码，低/高 32 源）                               | `sub_10092F34(irq)` 写点                                       |
| `0xA0060080/84`                  | 中断使能**清位**                                                           | `sub_10092A4C(irq, 0)` 写点                                    |
| `0x10021F50`                     | **ISR 分发器**：读 0xA07601A0 拿中断号 → 查 LISR 表 → 调用 → 写 0xA07601A8 | 反编译；整份镜像内**无调用者** → 由中断入口回调                |
| `0xF03D0310 + 12*irq`            | LISR 函数指针表（RAMF0，运行时填充）                                       | `sub_10021F50` 的 `12*v0 - 264436976`                          |
| `0xF03D0098 + 12*irq`            | LISR 名字表（断言 dump 用）                                                | `sub_10027878` 的 `- %s (LISR)`                                |
| `0x10092A08(irq, handler, name)` | LISR **注册**函数                                                          | `sub_10024390` / `sub_10070886` 调用点                         |

实测注册的中断号（LISR 名字）：**11 = "OSTD handler"（OS timer，tick 候选）、
12 = "FM handler"、18 = "GPT handler"**。

**异常向量表**：MAUI 镜像开头 `0x10020300` 就是 8 项 ARM 向量表
（`ldr pc,[pc,#0x18]`），运行期被拷到**低 RAM 0x0**（实测停机 dump 确认）。
其中 IRQ 槽（+0x18）→ **`0x700096B0`**，FIQ → 0x204，ABT → 0x244/0x264/0x2A0/0x2C0。

**`0x700096B0` 是固件自己的 ARM 中断入口**（不是我们要合成的）：
MAUI crt0 会把 flash `0x872548` 起 `0x20A8` 字节整段拷到 SRAM `0x70008000`，
其中 `0x700096B0` 处是 ARM 代码（用 ARM 模式反汇编才正确）：

```asm
700096B0: push {r1}
700096B4: mrs  r1, spsr
700096B8: tst  r1, #0x80      ; 中断前 CPU 是否关中断（CPSR.I）
700096BC: pop  {r1}
700096C0: subsne pc, lr, #4   ; 是 → 直接返回（不嵌套）
700096C4: push {r0-r3}        ; 否则保存现场继续
```

### 模拟器侧的中断交付（已实现，opt-in）

Unicorn 2.1.4 **没有注入中断的 API**，所以手工模拟 ARM 的 IRQ 异常：
`--tick=N` 每 N 条指令置一次 pending（中断号 `--tick-irq=`，默认 11=OSTD），
交付时保存 r0-r12/sp/lr/cpsr → 切 IRQ 模式（ARM、I=1）→ 写 SPSR_irq →
PC = `0x700096B0`、LR_irq = 中断点+4（桩用 `subs pc,lr,#4` 返回）。
**两个实测踩过的坑**：
1. `UC_ARM_REG_SPSR` 写的是**当前模式**的 SPSR —— 必须先切 IRQ 模式再写，
   否则写到 SPSR_svc，异常返回会恢复出错误 CPSR（T 位丢 → 走 ARM 解码 → 非法指令）
2. 交付前必须检查 **CPSR.I**：I=1 时真机不交付。否则中断入口按 SPSR.I 早退、
   pending 不清 → **中断风暴**（实测每 7 条指令一次）

* 固件在收尾处（`sub_1002E358`）确实写了 `0xA0030000 |= 0x2201`（开控制器）
* 但**CPU 的 CPSR.I 全程为 1**（采样 100M 条无一次翻转）→ 真机也不会在此交付中断
* ⇒ 「启动 OS 调度」的那段代码正是 `--ramf0-lr` 旁路掉的 RAM 补丁调用
  （`0x100283E0` → `0xF072BD7C`），两个未解问题在这里合流：**RAM 补丁区到底该由谁装载**

### 0xA0520000 = 传输/DMA 引擎（2026-10-07 重写：它是**装载引擎**，不只是 DMA）

MAUI ALICE 初始化（XIP `0x100324b8` 起）实测的完整寄存器序列：

| 偏移        | 实测值                                          | 含义                                                                  |
| ----------- | ----------------------------------------------- | --------------------------------------------------------------------- |
| +0x00       | `0x10947980`                                    | **解压目标起址**（= 后面 CAKE 校验的目标）                            |
| +0x04       | `0x10F39680`                                    | 解压目标终址（起始 + 长度后对齐到 64）                                |
| +0x08       | `0x10DA1A68`                                    | **mapping 表绝对地址**（= ALICE blob 头 +0x0C 的 u32，反汇编确认）    |
| +0x0C       | `0x00002000`                                    | 喂进数据窗口的字节数                                                  |
| +0x10~+0x28 | 4,6,8,9,b,c,d                                   | **区间寄存器初值**（ALICE blob 头 +0x14 起的 7 个 u16，逐个断言 <32） |
| +0x2C       | `0x00000FFF`                                    | 块大小 − 1（块 = 0x1000）                                             |
| +0x32       | `0x1000`（16 位）                               | **bank 号** = (blob 地址 >> 26) << 10（bank 4 = 0x10000000 窗口）     |
| +0x34       | 写 `0x80000001`                                 | 启动/状态，**轮询 bit31 = 就绪**（模拟器读侧恒应答）                  |
| +0x38       | `0x1`                                           | 收尾                                                                  |
| +0x3C       | `0x9`                                           | 低 4 位 = 调用方参数（其余位保留）                                    |
| +0x80/+0x84 | `0x90000000` / `0x10000000`，再 `+0x80 = 1`     | blob 头 +0x22/+0x23 低 4 位 << 28 + 启动（bit0）                      |
| +0x1000~    | 数据窗口（MAUI 成片写 `0xA0521000~0xA0521A7x`） | **字典**（2×Σ2^v 字节）从这里喂进                                     |

触发在 `0xA0530004`：写 3 = 复位、**写 19 = 启动解压**（MAUI sub_1003A448 先 19 后 3；
BL 0x10008994 共用同一引擎接口）。源 blob 由 **bank 号（+0x32）+ mapping 绝对地址
（+0x08）** 在镜像里唯一锁定（模拟器 `findAliceBlob` 按此双匹配，不再硬编码地址）。

**关键认知**：这个引擎是把**压缩数据装载到 `0x10947980` 起的区域**（约 10.4MB），
装载完固件直接执行它 —— 所以 `0x10947980` 在真机是 **RAM**，不是 NOR XIP
（`0x100216e4` 有个函数硬编码返回 `0x10947980`，与 DMA 配置互证）。

装载后固件校验 `*(0x10947980) == "CAKE"`（XIP `0x10032714`），不等就
`bl 0x1007bd0e`（assert 失败）→ fatal error → **关机**（详见 HANDOFF §9.8）。
模拟器现按上述协议实现引擎模型（`aliceDecodeToTarget`：消费固件配置的寄存器 →
alice.zig 解码 → 写目标窗口），实测固件 CAKE 校验通过、正常执行解压出的 OS 代码。
固件全程不执行解压循环（配寄存器 → 触发 → 轮询 → 校验），即真机上这是硬件引擎，
不是 CPU 上的软件解码器。

### MAUI 入口（第 4 阶段起点）

`★ MAUI` 取指 0x10020300，UART3 实测输出：

```
Bye bye bootloader, jump to=0x10020300
@ HW=MT0000 , SW=MT625:
# HW=MT0000 , SW=MT625:      ← 之后反复打印同一行（当前卡点）
```

**2026-10-06 更新**：上面那个打印死循环是**芯片识别失败**的表现（见「0xA0000000」
一节），接上 0xA0000008=0x625A 后消失。MAUI 现在一路跑到 `0x1002E38A` 的 `b .`，
等定时器 IRQ（详见 HANDOFF.md §4.4 与 §9）。

## LCM/LCD（第 5 步）

- **MT6250 实际**：LCM 控制器 `0xA0450000`：0xC00=命令/数据口（bit31=命令，
  0x80000028/0x38/0x89 = LCM 初始化命令），0xA0450000=状态（bit31 忙），
  0xA0450080=控制；数据口连写即帧传输，**320×240 RGB565**
- 图层机制（0x09000000）与真显存 0xE0000000 的关系待实测

## RTOS 地标（第 4 步，仅供参照、不抄做法）

- OS idle 循环 `0x1008F9C8`（ARM）轮询就绪标志 0xF05DDF64/0xF05DDF40，
  真实系统由 **GPT tick 中断服务置位**——第 4 步的正路是做定时器+中断
- 中断嵌套计数、调度器栈 0xF0424000
- 显示驱动命令队列崩溃点 `0x1007F4DA`（跳级启动、ExtBL 初始化没跑导致的
  负地址 0xFFFFFFC8）——第 5 步验收地标

## 教训（来自对方总结，路线纪律）

1. 跳过任何一级初始化 → 远处炸出不可解释的状态（命令队列 -1、基址 0）
2. 每轮点补会让模拟器变成补丁考古现场（7583 行、761 轮）
3. 正路：外设按手册/接线给行为，初始化自然跑完；stub 永远要有名字与依据
